## 1. HTTP 보안 헤더 7종 — Nginx 단일 위치에서 일괄 주입

### 문제

- `X-Frame-Options` 미설정 → 클릭재킹 공격에 무방비
- `Content-Security-Policy` 미설정 → XSS 시 외부 도메인으로 데이터 유출 가능
- `X-Content-Type-Options` 미설정 → MIME sniffing 으로 인한 우회 위험
- `Referrer-Policy` / `Permissions-Policy` 미설정 → 추적 정책 미정의

### 해결

`docker/nginx/conf.d/default.conf` 의 `server { listen 443 ssl ... }` 블록에 다음 헤더를 `always` 옵션으로 일괄 주입. `always` 는 5xx 응답에도 헤더 보장.

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(self), camera=(), microphone=(), payment=()" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' https://dapi.kakao.com https://t1.daumcdn.net https://*.daumcdn.net https://www.googletagmanager.com https://www.google-analytics.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://cdn.jsdelivr.net; img-src 'self' data: blob: https: http://t1.daumcdn.net; connect-src 'self' https://dapi.kakao.com https://cdn.jsdelivr.net https://www.googletagmanager.com https://www.google-analytics.com https://*.google-analytics.com https://*.analytics.google.com; font-src 'self' data: https://fonts.gstatic.com https://cdn.jsdelivr.net; frame-ancestors 'self'; base-uri 'self'; form-action 'self'" always;
add_header X-Request-ID $request_id always;
```

### 설계 의도

- **CSP**: 카카오맵 SDK (`dapi.kakao.com`, `t1.daumcdn.net`, `*.daumcdn.net`), Pretendard 폰트 CDN (`cdn.jsdelivr.net`), Google Tag Manager / GA4 (`www.googletagmanager.com`, `www.google-analytics.com`, `*.google-analytics.com`, `*.analytics.google.com`) 만 화이트리스트. 그 외 외부 스크립트는 모두 차단.
  - GTM 컨테이너(`gtm.js`)와 GA4 태그(`gtag/js`)는 모두 `www.googletagmanager.com` 에서 로드되므로 `script-src` 에 추가. GA4 수집 비콘(`/g/collect`)은 `connect-src` 의 analytics 도메인으로 전송. 픽셀 비콘은 기존 `img-src https:` 와일드카드로 이미 허용됨.
- **X-Frame-Options: SAMEORIGIN**: 동일 출처 iframe 만 허용 (관리자 UI 내 iframe 패턴 보존).
- **Permissions-Policy**: 위치 권한은 self 만, 카메라·마이크·결제 전부 차단.
- **HSTS**: `max-age=31536000` 으로 1년. 한 번 HTTPS 접속하면 브라우저가 그 다음부터 HTTP 요청을 차단.

### 검증

```bash
curl -sI https://kwueats.kro.kr | grep -i -E "x-frame|content-security|x-content-type|referrer-policy|permissions-policy|strict-transport"
```

## 2. `X-Powered-By` 헤더 노출 차단

### 문제

응답 헤더에 `X-Powered-By: Next.js`, `X-Powered-By: Express` 가 노출되어 프레임워크·버전 정보가 외부에 드러난다. 공격자가 알려진 CVE 를 빠르게 매칭할 수 있는 정보다.

### 해결 — 다중 방어

**1) Nginx 단에서 차단** (`docker/nginx/conf.d/default.conf`)

```nginx
proxy_hide_header X-Powered-By;
```

각 `location` 블록과 `server` 블록 양쪽에 적용.

**2) NestJS / Express 단에서 제거** (`apps/api/src/main.ts`)

```ts
const app = await NestFactory.create<NestExpressApplication>(AppModule);
app.disable('x-powered-by');
```

**3) Helmet 으로 추가 보호** (`apps/api/src/main.ts`)

```ts
import helmet from 'helmet';
app.use(helmet({
  contentSecurityPolicy: false,    // Nginx CSP 와 충돌 방지
  crossOriginEmbedderPolicy: false, // 카카오맵 SDK 호환
}));
```

### 의도

Nginx 만 제거해도 외부 노출은 막히지만, **API 가 직접 노출 (예: VPC 안 다른 서비스에서 호출)** 되는 시나리오까지 대비해 NestJS 단에도 제거. 패키지로는 `helmet` 추가.

### 검증

```bash
curl -sI https://kwueats.kro.kr | grep -i "x-powered-by"
# 출력 없음 = 정상
```

## 3. 에러 응답 정규화 — 스택·내부 정보 노출 차단

### 문제

기존 `HttpExceptionFilter` 는 NestJS 의 `HttpException` 만 catch 했고, 그 외 런타임 에러 (DB 연결 실패·null 참조 등) 는 NestJS 기본 핸들러가 처리하면서 스택 트레이스 일부가 응답에 포함될 가능성이 있었다. 또 에러 응답 포맷이 일관되지 않아 프론트엔드 분기 처리가 어려웠다.

### 해결

#### 3-1. `AppError` 커스텀 에러 클래스 도입

**파일**: `apps/api/src/common/errors/app-error.ts` (신규)

- `AppErrorCode` (열거형): UNAUTHORIZED / FORBIDDEN / NOT_FOUND / VALIDATION_FAILED / CONFLICT / RATE_LIMITED / INTERNAL_ERROR / EXTERNAL_DEPENDENCY_FAILED 등 안정적 식별자
- `AppError extends HttpException`: code/message/status 를 한 번에 표현
- 자주 쓰는 패턴은 서브클래스로 노출: `NotFoundError`, `InvalidCredentialsError`, `ForbiddenError`, `ConflictError`, `ExternalDependencyError`

사용 예:
```ts
throw new NotFoundError('식당을 찾을 수 없어요');
throw new AppError(AppErrorCode.RATE_LIMITED, '잠시 후 다시 시도해주세요', 429);
```

#### 3-2. `AllExceptionsFilter` 도입 — 전역 catch + 응답 정규화

**파일**: `apps/api/src/common/filters/all-exceptions.filter.ts` (신규)

```ts
@Catch()  // 인자 없는 @Catch() = 모든 예외 catch
export class AllExceptionsFilter implements ExceptionFilter { ... }
```

응답 본문은 **항상** 다음 형태로 정규화:
```json
{
  "code": "NOT_FOUND",
  "message": "식당을 찾을 수 없어요",
  "requestId": "<X-Request-ID 와 동일>",
  "timestamp": "2026-05-22T...",
  "path": "/api/restaurants/xyz"
}
```

핵심 정책:
- **`AppError`**: code/message/status 그대로 사용
- **`HttpException`** (NestJS 표준): status → code 매핑 테이블로 변환 (`400 → BAD_REQUEST` 등)
- **그 외 (런타임)**: production 에선 `'일시적 문제로 요청을 처리하지 못했어요...'` 로 모호하게 응답. 실제 메시지·스택은 서버 로그(`logger.error`) 에만
- 5xx 는 ERROR 레벨 로그 (스택 포함), 4xx 는 WARN 레벨 (스택 제외)
- `Nginx` 가 발급한 `X-Request-ID` 헤더를 그대로 응답에도 echo → 사용자가 장애 신고 시 같은 ID 로 서버 로그 추적 가능

#### 3-3. `main.ts` 에 등록

```ts
app.useGlobalFilters(new AllExceptionsFilter());
```

기존 `HttpExceptionFilter` 는 유지하되 등록 해제. 추후 정리.

### 의도

- 에러 응답이 항상 같은 shape → 프론트 분기 일관성
- 운영 환경에서 절대 내부 정보 노출 없음
- `requestId` 가 로그와 응답에 모두 박혀 있어 디버깅·민원 대응이 빠름

### 검증

```bash
# 의도적으로 잘못된 요청
curl -s https://kwueats.kro.kr/api/restaurants/xxx-nonexistent
# 응답: {"code":"NOT_FOUND","message":"...","requestId":"...","timestamp":"..."}
```

## 4. Rate Limiting — Nginx `limit_req_zone`

### 문제

무차별 요청 (로그인 brute-force, API 폭주) 에 대응할 단일 정책 없음.

### 해결

`docker/nginx/conf.d/default.conf` 최상단에:

```nginx
limit_req_zone $binary_remote_addr zone=api_zone:10m rate=10r/s;
limit_req_zone $binary_remote_addr zone=web_zone:10m rate=30r/s;
```

각 `location` 에 `limit_req zone=... burst=... nodelay;` 로 적용:

| 경로 | rate | burst | 설명 |
|---|---|---|---|
| `/api/` | 10r/s | 20 | API 호출 — 일반 사용자에 충분, 봇 차단 |
| `/_next/static/`, `/` | 30r/s | 60 | 정적 자산·페이지 |

NestJS 안의 `ThrottlerModule` (60s/100req) 도 유지되어 다중 방어.

### 의도

- IP 기준 제어 (`$binary_remote_addr`) — CDN 뒤가 아니라 가능
- `burst=20 nodelay` — 단기 폭증 20요청까지 즉시 처리, 그 이상은 503
- `10m` zone → 약 16만 IP 추적 가능 (충분)

### 추후 강화 (Phase 2)

- `/api/auth/login` 만 별도 zone (1r/s, burst=3) 으로 더 엄격하게
- `X-RateLimit-*` 표준 헤더는 Nginx OSS 가 기본 미제공 → headers-more-nginx-module 추가하거나 NestJS Throttler 의 헤더 사용

## 5. JWT 만료 시간 단축 + env 변수화

### 문제

기존 `auth.module.ts` 에 `expiresIn: '7d'` 가 하드코딩. 7일은 너무 길어 토큰 탈취 시 노출 윈도우가 크다.

### 해결

**`apps/api/src/auth/auth.module.ts`**

```ts
signOptions: {
  // 기본 1d. refresh token 도입 시 더 단축 권장.
  expiresIn: config.get<string>('JWT_EXPIRES_IN', '1d'),
}
```

**`apps/api/src/config/env.validation.ts`** 에 검증 추가:

```ts
JWT_EXPIRES_IN: Joi.string()
  .pattern(/^\d+(s|m|h|d|w)$/i)  // '1y' 같은 과도한 값 차단
  .default('1d'),
```

`.env.production` 에 `JWT_EXPIRES_IN=1d` 명시 가능. 미명시 시 1일.

### 의도

- 운영 정책을 코드 변경 없이 env 로 조정
- 정규식으로 `1y`, `999d` 같은 과도한 값 방지
- 7d → 1d 단축으로 탈취 노출 윈도우 7배 감소

### 추후 강화

- Refresh token + 짧은 access token (15분) 패턴
- 로그아웃 시 server-side 토큰 폐기 (Redis blacklist)
- HttpOnly Secure SameSite 쿠키로 저장 (localStorage 탈피)

## 6. env validation 완화 — AWS S3 optional 화

### 문제

기존 schema 는 `AWS_REGION/ACCESS_KEY_ID/SECRET_ACCESS_KEY/S3_BUCKET` 4개를 모두 `required()` 로 강제. EC2 단독 배포·S3 미사용 환경에서 API 가 부팅 시 `Config validation error` 로 죽었다 (운영 배포 중 실제 발생).

### 해결

**`apps/api/src/config/env.validation.ts`**

```ts
AWS_REGION: Joi.string().optional().allow(''),
AWS_ACCESS_KEY_ID: Joi.string().optional().allow(''),
AWS_SECRET_ACCESS_KEY: Joi.string().optional().allow(''),
AWS_S3_BUCKET: Joi.string().optional().allow(''),
```

S3 미사용 시 빈 값으로 두면 통과. 실제 업로드 코드에서 값 존재 여부 분기.

### 의도

- 인프라 선택지 확대 (S3 / 로컬 디스크 / MinIO)
- 부팅 실패 위험 감소

## 7. 민감 필드 로깅 마스킹

### 문제

기본 access log 에 request body 가 포함될 경우 `password`, `accessToken`, 카드번호 등 PII·secret 노출 위험.

### 해결

**`apps/api/src/common/interceptors/sensitive-fields.interceptor.ts`** (신규)

`SensitiveFieldsInterceptor` — 전역 인터셉터:

- 요청 시작 시 method/url/requestId 기록
- 응답 완료 시 elapsedMs 추가 로깅
- 본문(body) 자체는 로그에 안 박지만, **만약 다른 로거가 body 를 출력하려 한다면** `SensitiveFieldsInterceptor.mask(body)` 정적 메서드 호출로 안전하게 마스킹 가능

마스킹 대상 키 (lowercase 부분 일치):
- `password`, `passwordHash`
- `token`, `accessToken`, `refreshToken`, `jwt`
- `secret`, `apiKey`, `apiSecret`
- `authorization`, `cookie`
- `cardNumber`, `cvv`, `ssn`

```ts
// 사용 예
const safe = SensitiveFieldsInterceptor.mask(req.body);
logger.debug(safe);
```

`main.ts`:
```ts
app.useGlobalInterceptors(new SensitiveFieldsInterceptor());
```

### 의도

- 비밀번호·토큰이 로그에 평문으로 남는 사고 예방
- 깊이 5 까지 재귀, 그 이상은 절단해 폭주 방지
- 정적 메서드로 노출해 다른 로거에서도 재사용

### 추후 강화 (Phase 2)

- pino + nestjs-pino 도입 → 구조화 로그 JSON
- pino redact 옵션으로 동일한 키 패턴 자동 마스킹

## 9. Request-ID 추적 체계

### 문제

장애 발생 시 사용자가 "에러 났어요" 만 신고하면 어느 요청인지 추적 어렵다.

### 해결 — 3단 연동

**1) Nginx 가 매 요청에 발급** (`$request_id`)
```nginx
add_header X-Request-ID $request_id always;
proxy_set_header X-Request-ID $request_id;
```

**2) NestJS 가 헤더로 수신 + 응답에 echo**

`AllExceptionsFilter` 안에서:
```ts
const requestId = request.headers?.['x-request-id'] ?? globalThis.crypto.randomUUID();
response.setHeader('X-Request-ID', requestId);
// 응답 body 에도 포함
response.json({ ...payload, requestId, ... });
```

**3) 로그 출력 시 항상 포함**

```ts
this.logger.error(JSON.stringify({ requestId, method, path, status, code }), stack);
```

### 의도

사용자 → 응답 header `X-Request-ID` 확인 → 운영자 → 같은 ID 로 서버 로그 grep → 1초 안에 해당 요청 컨텍스트 복원.
